# 武器与战技限制排查（2026-11-13）

## 已核实的数据

原版更新 131072 的 `GameData/Job.bin` 中，职业记录从文件偏移 `0x10e0` 开始，每条 `0x230` 字节。职业对象 `+398..+404` 依次是剑、枪、斧、弓、拳套、黑魔法、白魔法的有符号许可值。`-1` 会在装备和普通攻击的原生检查中拒绝相应武器；`0` 与正数的其他含义尚不能一概而论。剑士七项为 `[2,0,-1,-1,-1,-1,-1]`，重装步兵为 `[0,1,1,-1,-1,-1,-1]`，斗拳手为 `[-1,-1,-1,-1,2,-1,-1]`，无职为七项 `0`。

原版 `GameData/Item.bin` 的七种普通装备样本如下。类型值来自各物品记录 `+0x40`；附带项来自记录 `+0x90` 的列表。

| 类别 | 样本 | 类型值 | 自带技能或效果 |
| --- | --- | ---: | --- |
| 剑 | 铁剑 | 0 | `SID_剣スキル` |
| 枪 | 铁枪 | 1 | `SID_騎兵有効` |
| 斧 | 铁斧 | 2 | `SID_斧スキル` |
| 弓 | 铁弓 | 3 | `SID_飛行特効` |
| 拳套 | 铁拳套 | 4 | `SID_籠手スキル` |
| 黑魔法 | 火焰 | 5 | `SID_雨天炎弱体` |
| 白魔法 | 治疗 | 6 | `SID_回復魔法`、`SID_持ち替え対象` |

`Item.bin` 没有 `JID_` 职业 ID 字符串。普通铁斧的附带列表没有 `SID_戦技不能武器`。这说明没有发现“铁斧直接列出禁止剑士”的字符串式职业名单；仍不能排除数值标志或运行时代码中的限制。

原版 `GameData/Skill.bin` 中，“劈刺”是 `SID_スパイク`，记录偏移 `0x13a6a0`。它的 `+0x80` 条件列表引用 `SID_斧`，`+0x90` 列表引用 `SID_戦技不能武器`；剑战技“刚击”的对应类型条件引用 `SID_剣`。`Skill.bin` 也没有 `JID_` 字符串。此前临时移除“劈刺”的这两个列表后仍未变亮，不能把当前拒绝点简单认定为这两项。

## 实机对照

- 关键定位：隔离版只把 `Job.bin` 中剑士记录的斧许可从 `-1` 改为 `1`（文件偏移 `0x23f0`，其他字节未动），在游戏启动前作为 RomFS 覆盖加载。古扎岚重新读档后，状态页“技能 LV”出现斧，“劈刺”变亮并成功施放。说明职业许可在角色／战斗数据初始化阶段参与技能类别与战技可用性构建；此前运行中临时改内存但未生效，不能否定这条初始化路径。此覆盖仅为隔离诊断，不属于正式 MOD。
- 后续确认：F1 开启时只在运行中同步职业对象与角色缓存，即使五类武器都出现在“技能 LV”，古扎岚的“劈刺”仍灰；重新读战斗存档及战前存档后仍不行。因此职业许可必须更早参与游戏数据加载。现已在 RomFS 读取阶段按选项把 `Job.bin` 中五种物理武器许可的 `-1` 替换为 `1`，仅在文件布局与原字节匹配时生效。隔离进程的剑士职业对象与角色缓存读回 `[2,0,1,1,1,-1,-1]`。实机确认古扎岚剑士使用铁斧时“劈刺”变亮并成功施放，西洛可牧师使用剑战技也成功施放；两人攻击后对应的斧、剑熟练经验均有增长。此方式需要重启游戏才能刷新已加载职业数据。

- F1 选项开启后，剑士古扎岚与牧师西洛可可以装备普通铁斧，普通武器攻击可执行。
- 古扎岚背包中有耐久至少 3 的普通铁斧、已学并装备“劈刺”时，该战技仍是灰色且不能施放。
- 穆当前是斗拳手，职业斧值不是正数；手持铁斧时拳战技亮，剑和斧战技灰。
- 巴卡尼亚当前是重装步兵，职业斧值为 `1`，已学“劈刺”；手持普通铁斧时“劈刺”变亮且可以施放。
- 古扎岚的斧熟练度为 C+，巴卡尼亚为 B+；古扎岚的“劈刺”灰色不能用，因此不能用“斧熟练度为零”解释。古扎岚的状态页已装备铁斧、特技中有“斧术 LV2”，但右下“技能 LV”没有斧；西洛可作为牧师已装备剑、特技中有“剑术 LV1”，右下“技能 LV”也没有剑。两张截图说明装备许可与技能等级显示存在独立过滤。
- 在隔离测试进程里，曾把古扎岚职业表和角色缓存中的斧值同时临时设为 `1`，重新读档后“劈刺”仍灰且不能施放。两处内存值已恢复。此前设为 `0` 也没有效果。
- 职业记录 `+420..+426` 另有七个武器等级参数；剑士斧项 `+422` 原值 `0`，重装步兵斧项是 `5`。代码 `f_71006d61a0` 会将角色武器等级提高到该职业参数规定的下限。隔离测试把剑士斧项临时设为 `5`，单独测试及与斧许可 `1` 组合测试后，“劈刺”仍灰且不能施放。所有临时内存值均已恢复，测试进程已关闭。
- 新增只读诊断分别监听普通装备检查 `f_71006ea680` 与普通战斗武器检查 `f_71006ea910` 的入口，并记录铁斧编号 `224` 和其他样本。古扎岚打开灰色“劈刺”列表时均未命中，说明这两个已解锁的入口没有参与该次菜单判定；不能据此断定战技候选列表为空，因为战技可能使用其他专用检查。诊断已从源代码撤除。

战斗操作顺序是先选择战技，再从背包选择用于释放该战技的武器。因此，战技列表左侧显示的铁斧不能证明铁斧已经通过该战技的武器候选检查。灰色可能表示战技菜单没有找到符合条件的背包武器；后续应定位候选列表生成和逐件武器的拒绝条件。

`f_71009b5c90` 在生成一份技能类别列表时，先读取角色缓存的 `unit + 812 + type` 职业许可值；前七类若为负数则跳过，之后再读实际等级 `unit + 540 + type`，等级为 0 或 12 也跳过。`f_71009501d0` 生成类似列表，还可能读取职业记录 `job + 398 + type`。这两处体现了游戏中存在“职业许可决定技能类别是否进入列表”的机制，但在古扎岚状态页和灰色战技菜单操作期间，两个函数的入口探针均未命中，因此它们不是那两处页面的直接构建函数。`f_71015a7640` 是另一处物品候选检查，读档初期被调用，但灰色“劈刺”以及成功施放的剑战技期间未再次调用；也不能将它当作当前战技拒绝点。

上述运行中改内存的失败曾使战技拒绝点难以确定。加载前修改职业表成功，说明职业许可还参与了角色或战斗状态的初始化；运行中改同一数值不足以重建这些状态。最终隔离版中，用户让穆和古扎岚在城镇训练原职业不允许的武器，确认两人取得熟练经验、**新学会此前未习得的对应武器战技**，并可装备、在战斗中释放。

## 代码状态

已保留装备与普通武器使用钩子，并加入职业表加载时的五类武器许可补丁。运行中的职业／角色缓存同步和所有战技诊断探针已从源代码移除。F1 设置可保存，完整效果须重启游戏。早期全职业版本中，剑士、牧师的跨职业武器战技及城镇训练获取新战技均通过隔离实机回归。2026-11-14 起解锁范围缩小为步兵系，见下文；新范围的两项实机检查也已由用户确认。

## 飞鸵兵骑乘动画兼容性（2026-11-14 用户反馈）

原版 `Job.bin` 的 `JID_飛駝兵`（记录 6，偏移 `0x1e00`）在剑／枪／斧／弓／手甲／黑魔法／白魔法上的许可为 `[0,1,0,-1,-1,-1,-1]`；下马形态（记录 7）同样将弓与手甲列为 `-1`。当前解锁补丁只把前五类的 `-1` 改为 `1`，没有新增动画、武器持握位置或坐骑骨骼配置。用户报告骑乘时使用手甲或弓，坐骑在原地穿模；两种武器恰好都是该职业原版禁用的类型。

这支持“未适配该骑乘职业与武器组合的战斗动作／挂点”这一解释，但现有证据不能区分缺少专用动作文件、退回了不合适的通用动作，还是现有动作与坐骑骨骼和武器挂点不匹配。下马形态的许可也为 `-1`，因此不能未经实测就假定自动下马能解决。本节的穿模现象来自用户反馈，尚未在当前测试版复现。

## 步兵系专用解锁范围（2026-11-14）

按用户决定，F1 功能改名「解锁步兵系职业武器/战技限制」，原设置键 `remove_weapon_restrictions` 保留以继承已有开关值。职业表加载补丁与运行时装备／使用钩子统一使用同一分类规则：职业角色标签 `+0x38` 为攻势／防卫／援护／魔道／连携之一、坐骑字段 `+0x68` 为空，且职业 ID 不以「下馬」结尾。这样骑兵、飞行系、战车以及骑乘法系的骑乘和下马形态都保留原版七类武器许可；未知标签和非人物职业也不解锁。原版 137 条连续职业记录中，该规则选出 40 条步兵记录，其中五类物理武器有 123 个原本为 `-1` 的许可字节可补。飞鸵兵、骑甲鸵兵、轻骑兵、战车兵、骑乘法系及其下马形态均被排除。静态分类、编译与启动记录检查通过；用户在独立测试版确认飞鸵兵骑乘时弓和手甲恢复为不可装备／使用，且步兵跨职业武器与战技仍可用。原穿模的具体动画原因尚未查明。

## 对外部技术推测的核对

用户提供的 `FEFW_Wing_Knight_Mod+v1.0.0.zip` 只读解包对照：它包含 `GameData/Job.bin`、`Skill.bin`、纹理及多语言文本，没有主程序或运行时补丁。原版有 137 条连续职业记录，该 MOD 新增 2 条，成为 139 条。新增职业记录的七类许可值为 `[1,2,-1,-1,-1,-1,-1]` 与 `[1,1,-1,-1,-1,-1,-1]`，对应技能等级下限前两项分别为 `[7,7]` 与 `[0,0]`。这说明自制兵种沿用职业许可数组，不提供“全武器职业”的现成设置；其 `Skill.bin` 也有新增记录。与原版静态代码交叉看，它支持技能等级列表按职业许可过滤的判断，但这个 MOD 不能证明战技菜单也采用同一过滤。

`Job.bin` 文件头 `+12` 的 176（兵种 MOD 中为 178）不是职业数，而是文件尾部第一组 8 字节索引项的数量；文件头 `+8` 的 2981（MOD 中为 3006）是紧接着第二组索引项的数量。原版 `+4` 指向 `0x19bd8`，两组索引项连同 32 字节区域占据 `32 + 176×8 + 2981×8` 字节，恰好在首个 `JID_` 字符串的 `0x1fea0` 处结束。真实职业对象从 `0x10e0` 开始，每条 `0x230` 字节，顺序 ID 位于对象 `+16`；原版索引 `0..136` 共 137 条，索引 137 开始已是其他结构。公开资料所列 60 个职业中，初级至神将的 58 个名称均能在这 137 条中找到；“平民／贵族”未以两个独立的 `JID_` 名称出现，基础项为“無職”。其余还包括下马形态、敌方和特殊单位。补丁已改为按对象顺序 ID 识别职业记录，不再把文件头的 176 当职业数。

用户提供的两段 Gemini 说明可作为排查项目，但其中 `AllowedClassFlags`、`ClassTypeReq`、`RequiredClassID`、`0xFFFF`、职业结构 `0x40`、武器结构 `0x30` 均未从本作原版文件或代码得到证实，不能据此批量修改。实际 `Job.bin` 职业记录步长已确认是 `0x230`；现有两条武器检查实际读取的是职业对象七个有符号字节，并根据负值拒绝，不是文中举例的单个武器准入位掩码。武器或战技数据存在其他标志/标签的可能性仍需逐项验证。文中以“当前手持武器”判定战技的示例也不符合本次实机操作顺序：本作先选战技，随后再选背包中的对应武器。

任天堂开发者访谈确认本作沿用了《风花雪月》的自由转职机制，并确认各角色可学内容有差异，但没有公开 `AllowedClassFlags`、`RequiredClassID` 或“本作使用 Katana Engine”的具体说法。所引游侠网和 360 游戏页面是玩法攻略，没有提供二进制结构与代码依据。引擎与动画资产的具体推断不能替代对本作数据和运行逻辑的验证。
